# Pi IntelliSense — alternative standalone-viewer architecture (not selected for v1)

**Primary implementation specification: [../SPEC.md](../SPEC.md).** The primary design integrates directly with the existing `pi-tab-focus` visual cursor and a versioned bridge, matching the requested in-chat `K`/`gd` experience. This document is an **optional fallback proposal** for a dedicated code viewer if upstream bridge integration proves infeasible. It is not the v1 contract, and disagreements defer to the primary specification.

Status: **alternative design only** · 2026-10-23  
Target: Pi interactive TUI, LSP servers and a *running* Neovim instance  
Scope of this alternative: a standalone Pi extension requiring no changes to `pi-tab-focus`.

## 1. Objective

Make code quoted or returned in a Pi conversation navigable like an editor: place a keyboard cursor on a symbol, press `K` for language-server hover, `gd` for definitions, `gr` for references and optionally `<C-Space>` for completion. Choosing a destination opens the **actual source file at the exact line and column in an already-running Neovim instance**.

This is not an agent-side LSP tool. Responses come from a language server directly to the user-facing terminal UI and navigation must not trigger a model turn.

### Non-goals for v1

- Editing Pi's built-in transcript renderer or taking over its existing scrollback.
- Pretending arbitrary prose/code generated by a model has a known disk location.
- Starting Neovim automatically, hijacking a random Neovim server or guaranteeing OS focus.
- Applying completion edits to disk, renaming symbols, code actions or edits through Pi.
- Reimplementing Neovim's or an LSP server's syntax engine.
- Modifying the source document just to satisfy a language server.

## 2. Verified upstream affordances and limits

Pi exposes `pi.registerCommand`, `pi.registerShortcut`, lifecycle `pi.on`, `ctx.sessionManager.getBranch()` and `ctx.ui.custom()`. A custom UI component renders terminal lines, owns keys and can use mouse events in **fullscreen** mode. In regular TUI mode the terminal owns the mouse and scrollback; therefore there is no reliable arbitrary mouse hover in ordinary transcript text. `ctx.ui.custom()` temporarily owns an interactive area: it does **not** turn all pre-existing Markdown code fences into focusable code editors. Standard tool/message renderers and Markdown transformers are display hooks, not a supported general hit-testing and focus contract. Pi extensions load in print, JSON and RPC modes, where custom terminal components are unavailable.

Consequently, v1 is an **explicit navigator** opened by `/intellisense` (alias `/intel` if registration permits) or an optional global shortcut. A picker lists code blocks from the **active session branch**; choosing one opens a navigable read-only code view. Its behavior is identical whether a block came from assistant text or a tool result. Native click-to-inspect inside the original transcript is a separate v2 Pi-core integration/research item, **not** a promise of this extension.

Pi source/API compatibility must be checked against the installed Pi version before implementation. The current official documentation uses `@earendil-works/pi-coding-agent` and `@earendil-works/pi-tui`; older Pi forks use `@mariozechner/*`. **Do not assume both are interchangeable**. Keep Pi coupling behind one adapter.

## 3. User interaction

1. Invoke `/intellisense`. If no supported blocks exist, show a nonfatal notice.
2. Select a conversation code block from a list of message index, origin, language, path when known and first line. The active branch controls ordering; user can search/filter results.
3. A read-only code pane opens with a symbol cursor, line numbers and file/provenance status. `j/k/h/l`, arrows, `w/b`, `gg/G` navigate. Esc returns to Pi. Tabs expand visually but retain exact source offsets.
4. `K` requests `textDocument/hover`. A nonblocking overlay shows plain text/Markdown documentation, language, type and range if available. Esc closes the overlay without closing the code pane.
5. `gd` requests `textDocument/definition`. One destination opens the target in Neovim immediately; multiple locations open a selectable list. `gr` requests `textDocument/references` and opens a list. A location selection opens Neovim via RPC. Failures leave Pi and its current selection intact.
6. `<C-Space>` (when terminal supports it) calls `textDocument/completion` and presents a **read-only suggestion list**; completion acceptance changes neither the code nor disk in v1.
7. In Pi fullscreen, mouse **click** can set the code-pane cursor; **move/hover** can request documentation with debounce. Keyboard is fully functional regardless of terminal mouse support. Mouse never takes over selection/copy unexpectedly.
8. Show a reason for missing functionality: no source anchor, stale source, no server configured, unsupported server method, cancelled request, no Neovim socket, ambiguous location or unsafe path. Do not silently fall back to model-generated answers.

**V1 acceptance:** for a verified block anchored to an actual TypeScript/Python file, `K` displays an LSP response, `gd` resolves the target and Neovim displays the destination at the correct byte-column position. Unsupported/ambiguous blocks never jump to a guessed location.

## 4. Architecture

```text
Pi session active branch
  └─ message extractor (assistant Markdown + known read/tool outputs)
       └─ CodeBlock registry (session-entry/message identity + stable content hash)
            └─ SourceAnchor resolver + document snapshot validation
                 └─ Interactive CodePane (Pi ctx.ui.custom)
                      ├─ LSP supervisor (per project/language; JSON-RPC over stdio)
                      │    └─ hover / definition / references / completion
                      └─ Location selector and safety gate
                           └─ Neovim adapter (MessagePack-RPC to explicit socket)
                                └─ open file → set cursor
```

Modules and proposed API boundaries:

| Module | Responsibility | Test seam |
| --- | --- | --- |
| `src/pi-extension.ts` | Pi factory, commands, lifecycle, UI adapter, no long-lived work in factory | fake `ExtensionAPI` and `ExtensionContext` |
| `src/blocks.ts` | Branch-only message extraction, code-fence parser, registry, stable IDs | message fixtures |
| `src/provenance.ts` | Anchoring code spans to confirmed file + range, stale checks | injected filesystem |
| `src/positions.ts` | visual grapheme/terminal column ↔ UTF-16/32/8 position mapping | pure property/edge tests |
| `src/code-pane.ts` | keyboard, keyboard cursor, mouse hit testing, viewport, hover popover | fake TUI + terminal event fixtures |
| `src/lsp.ts` | protocol lifecycle, capability negotiation, pending requests and cancellation | in-memory JSON-RPC fake server |
| `src/locations.ts` | normalize Location/LocationLink, order, dedup, validate URI and bounds | pure tests |
| `src/neovim.ts` | resolve socket, MessagePack-RPC connection, safe file open, cursor position | fake RPC client + real Nvim smoke test |
| `src/controller.ts` | orchestrate stale-guarded hover/definition/open, cleanup and errors | fake LSP/UI/Neovim |
| `src/config.ts` | validated opt-in server mappings, workspace and socket policy | config fixtures |

No code pane should directly call `child_process`, edit source, infer an on-disk path from text alone or invoke a model.

### 4.1 Session extraction and identity

Read `ctx.sessionManager.getBranch()` only. On command execution, walk active branch entries in logical order, extract finalized text blocks from user/assistant messages and supported tool results, skipping thinking and unsupported binary attachments. Parse CommonMark fenced code (backticks or tildes, variable fence lengths, matching terminator) without incorrectly treating nested literals as fences. Preserve original newlines and parse language info without interpreting arbitrary fence attributes as authorization.

Identifier: `{sessionId, entryId, contentPartIndex, blockIndex, sha256(code)}`. If Pi entries lack a stable ID in the installed API, introduce deterministic branch-entry ordinal plus session path and content hash; reindex on branch change rather than accepting stale IDs. Cap block count and code size to avoid unbounded UI/LSP work (defaults 200 blocks per branch, 200 KiB/block). Explicitly distinguish display code from provenance and source files.

### 4.2 Provenance and snapshot integrity

A block carries `source: 'disk-verified' | 'virtual' | 'unknown'`, optional trusted canonical path, code range, recorded file hash/mtime and text snapshot.

- **disk-verified**: path from *structured, trusted tool metadata* or user-selected local file. If relying on `read` textual output, treat its path as a **hint**, not proof; resolve the path under workspace, read the file and match snippet exactly with unchanged line boundaries and indentation. A hint in assistant text is never proof. If multiple occurrences match, require explicit user choice. If the snippet is shortened, line-numbered, elided, reformatted or diff-styled, do not claim it matches disk.
- **virtual**: generated code with known language but no trustworthy file mapping. Open an unsaved LSP text document at an internal URI without creating files. Hover/completion may work; do not invent a file for `gd`. A server's concrete definition target may still be offered **only after target validation**.
- **unknown**: no recognized language or source and no configured virtual-document mode. Show code read-only with an explanation.
- Re-read and revalidate anchors before every request and *again before navigation*. If file contents or version mismatch, invalidate anchor and do not redirect to a possibly wrong location. Changed files need explicit reload/reselection.
- Do not follow symlinks outside allowed roots and do not allow path traversal or network/non-file URI schemes by default. Allow external dependencies only through explicit trusted-roots configuration or deliberate approval.

Identity/snapshot checks must prevent navigating stale definitions after session branch switch, reload or a second code block selection.

### 4.3 LSP client and server ownership

Prefer dedicated LSP connections managed by this extension; do **not** assume Neovim's builtin LSP RPC clients can be controlled through the terminal. Start allowlisted executables from explicit config using `spawn(command, args, {shell:false})`, working directory = verified project root. Example opt-in mapping: TS/JS → `typescript-language-server --stdio` plus local `typescript` package; Python → `basedpyright-langserver --stdio`. Validate executable resolution and server launch errors without crashing Pi. Prefer one server per `(root,languageFamily,config)`, not per block.

Use LSP JSON-RPC Content-Length framing (byte length), request IDs, request timeouts, cancellation (`$/cancelRequest`), stderr logging with redaction, server exit recovery and clean shutdown. Initialize capabilities (hover, definition LocationLink, references, completion, document sync and positionEncodings) then send `initialized`, `textDocument/didOpen`; send `didChange` with monotonically increasing versions if an explicit refresh changes the snapshot, and `didClose` on release. Honor server's `textDocumentSync` and provider capabilities. Advertise support only for functions actually implemented by the client. Default LSP positions to UTF-16 unless negotiated differently. Do not assume all servers accept untitled/virtual URIs.

Handle null, MarkedString and MarkupContent hover results; `Location`, `Location[]`, `LocationLink[]` and null definitions; null/array references and `CompletionList`/array completion. Sanitize hover Markdown (no executable raw HTML, terminal escape sequences or untrusted OSC hyperlinks). Results are advisory and cannot bypass path validation.

Latency budget targets (not assertions of performance): cursor movement immediate, show spinner after 100 ms, hover debounce ~150–250 ms, user requests cancellable, default LSP request timeout 5 s. Result display must ignore responses for a superseded block, cursor, snapshot, branch or request token. Never run LSP synchronously on render or streaming-message hooks.

### 4.4 Position mapping

LSP: 0-based line and **negotiated** character encoding (normally UTF-16). Neovim `nvim_win_set_cursor`: 1-based line and 0-based **UTF-8 byte** column. Terminal visual x uses grapheme display widths and tabs; combining marks, astral symbols, East Asian full-width characters, ANSI styling, soft wraps and line numbers change the screen mapping.

Define `lspToNvimByteColumn(lineText, character, encoding)` with bounded input, Unicode-safe conversion and rejection of invalid positions inside a surrogate pair. Map code-pane cursor to the corresponding original document position, including verified snippet start line and column if snippet not at file line 0. Never guess terminal display column equals LSP character or Neovim byte offset. Prefer querying the actual Neovim target buffer line after opening if it has unsaved changes; check that the chosen offset still points at the intended symbol, otherwise show warning.

### 4.5 Destination normalization and validation

Normalize a single `Location`, `Location[]` or `LocationLink[]` to `{uri, range, selectionRange}`; for LocationLink use `targetSelectionRange` and `targetUri` (not source origin). Do not confuse response order with validity. Dedup stable by canonical URI + line + character. Multiple distinct destinations always show a selector; zero gives an informational message.

Decode `file://` via a proper URL converter (percent encoding, Windows drive handling if later supported). Reject unsupported `http:`, `javascript:`, `command:`, `untitled:` and invalid file URIs for Neovim open. Canonicalize and realpath existing files and verify trusted roots with path-segment-aware containment (`/repo` must not allow `/repo-evil`). No `exec` string interpolation. Missing/unreadable target is an error, not a new empty file.

### 4.6 Neovim handoff

Resolve existing server in order: explicit extension config `nvimSocket`, `$NVIM` if connected from an embedded Neovim terminal. Do not enumerate and select an arbitrary socket; if none is available show setup instructions. Prefer a MessagePack-RPC client. Connect with bounded timeout; call a **constant** Lua RPC chunk via `nvim_exec_lua` with `[absolutePath, oneBasedLine, byteColumn]` as separate arguments, or use structured `nvim_cmd` with `magic={file:false,bar:false}` followed by `nvim_win_set_cursor`. For atomic multi-step navigation, single Lua call opens file via structured `nvim_cmd` then retrieves current buffer line and sets cursor. The path is data, never executable Ex/Lua or shell text. Respect unsaved-buffer safety and provide a clear error if Neovim refuses to switch buffers.

Open an existing file in the current Neovim tab/window by default; allow configurable `split`/`vsplit`/`tabnew` later. Neovim processes the RPC even if its terminal window is not foregrounded. **Focus-stealing is out of scope.** Maintain Pi view and cursor if the socket is dead or navigation fails. Do not call `nvim --server ... --remote +line`: Neovim's remote `+{cmd}` behavior differs from Vim and a subprocess `--remote-send` sequence is fragile.

### 4.7 Pi extension lifecycle

Register command/shortcut only inside factory. In `session_start`, initialize pure session state, not language servers. Lazily launch servers when navigating. On `session_shutdown`, abort pending requests, close virtual documents, shut down child servers and close RPC connections. When switching branch/session or reloading, invalidate block registry and snapshot generation. Ensure idempotent cleanup. Guard `ctx.mode === 'tui'` before `ctx.ui.custom`; in unsupported modes the command emits a meaningful response without throwing.

Keep config minimal: `languages` (extension/language ID to executable/args), `nvimSocket`, `trustedRoots`, `allowExternalDefinitions=false`, `hoverOnMouseMove`, timeout, resource caps. Default outbound execution disabled for unknown servers. No telemetry or transcript uploads.

## 5. Milestones

**M0 — adapter spike and API pinning:** check current installed Pi package exports and message shapes; make a tiny `ctx.ui.custom` code-pane POC, confirm fullscreen mouse event support and `getBranch()` entry types. Record tested Pi/Nvim versions.

**M1 — provenance/navigation core:** build fenced-code extraction and source anchor resolution, UTF-16/byte/visual-column mapping, robust target validation. Run pure unit tests.

**M2 — LSP:** JSON-RPC protocol, lifecycle, capability negotiation, servers, virtual/verified snapshots. Mock-server tests plus integration fixture on an installed language server.

**M3 — Neovim:** explicit socket/connection, safe RPC navigation, Unicode cursor positions, real `nvim --listen` smoke tests. Ensure no new Neovim instance or file is created.

**M4 — Pi UI:** command, branch picker, focused code pane, keyboard mappings, hover and results lists. Optional fullscreen mouse. Test fake Pi/TUI and manual acceptance with actual Pi.

**M5 — hardening:** cancellation/races, source staleness, symlinks, ANSI/Markdown sanitization, terminal modes, server restart, resource cleanup and accessibility.

## 6. Acceptance criteria

1. A matching anchored TS block can hover and go to definition in an existing Neovim server with correct UTF-8 byte-column, including non-ASCII text earlier on its line.
2. A virtual code block supports hover where the server supports virtual docs; never assumes a real file location.
3. Ambiguous, altered, stale or truncated snippets do not silently select a disk file.
4. Multiple definitions and references display choices; cancelling performs no Neovim call.
5. Keyboard interaction works in normal and fullscreen Pi TUI; mouse events are optional and fullscreen-only.
6. A session switch, model response update, hover race or disposal cannot open outdated destinations.
7. File URI, roots, symlink and Ex command injection tests pass; no shell is needed to open Neovim.
8. Pi noninteractive modes fail gracefully, editor not running reports configuration error and cleanup leaves no child servers.
9. Existing agent conversation is neither edited nor automatically sent to a model for navigation.
10. Test suite runs with `npm test` plus optional separately marked real Pi/Neovim integration tests.

## 7. Risks, alternatives and unresolved upstream checks

- **Biggest constraint:** standalone extensions cannot promise pointer-hover/`gd` on symbols in Pi's *built-in transcript*; v1 uses a code pane. Native transcript semantics require a Pi upstream API/core enhancement (per-block focus/selection, hit test, coordinates and stable source metadata).
- Pi package namespace and API type names may change. Pin and verify before production implementation; don't blend APIs from forks.
- Tool output snippets often contain line numbers and truncation. Never silently transform and claim source integrity.
- Neovim may be remote in tmux/SSH or not focused; `$NVIM` isn't always populated. Expose explicit socket config and diagnostics.
- Some language servers refuse arbitrary unsaved docs or require specific project configs. This affects hover on generated code.
- A v2 design could use a separate Neovim floating buffer showing conversation code with existing Neovim LSP and native `K/gd`; that makes Pi less interactive but is cheaper than patching its transcript renderer. Another v2 path is contribution to Pi's fullscreen TUI message component focus/hit-testing.
